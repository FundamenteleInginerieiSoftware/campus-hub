## Part 1: In simple terms

In distributed web applications, network glitches, mobile timeouts, and double-clicks regularly cause clients to retry HTTP POST requests. Without idempotency protection:
1. A student clicking "Book" on a spotty Wi-Fi connection might submit two identical requests.
2. If both succeed, the student consumes two active booking quota slots.
3. If one succeeds and the other fails on overlap, the student receives an error screen even though their reservation was successfully registered, causing panic and repeated clicks.

To eliminate this class of issues, we implemented a robust **Idempotency Framework** with **Request Fingerprinting**:
- **Client Header (`Idempotency-Key`)**: The client attaches a unique UUID in the HTTP header `Idempotency-Key` (e.g., generated per UI button click).
- **Request Fingerprinting (SHA-256)**: The server computes a SHA-256 digest of the user ID, HTTP method, target URI, and normalized request body.
- **Cached Replay**: If the same key is submitted again, the server intercepts the call and serves the original HTTP response status code and JSON payload directly from the database, accompanied by the HTTP response header `Idempotency-Replayed: true`.
- **Payload Mismatch Detection**: If a client attempts to reuse an existing idempotency key with different parameters (e.g. attempting to book a different asset or different time slot with an old key), the server rejects it immediately with HTTP 400 (`IDEMPOTENCY_KEY_PAYLOAD_MISMATCH`).
- **Concurrent In-Flight Guard**: If two identical requests hit the server concurrently within milliseconds, the first request atomically claims the key in the database with status `IN_PROGRESS`. The second request detects the in-progress state and is immediately rejected with HTTP 409 (`CONCURRENT_IDEMPOTENT_REQUEST`), preventing race conditions.

## Part 2: Technical details

### 1. Database Schema (`idempotency_records`)
Created in Flyway migration `V2026_11_10_0200__reservation_idempotency.sql`:
```sql
CREATE TABLE idempotency_records (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    idempotency_key VARCHAR(128) NOT NULL,
    user_id BIGINT NOT NULL,
    request_fingerprint VARCHAR(64) NOT NULL,
    status VARCHAR(32) NOT NULL,
    response_status INTEGER,
    response_body TEXT,
    created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    expires_at TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    CONSTRAINT uq_idempotency_key_user UNIQUE (idempotency_key, user_id),
    CONSTRAINT fk_idempotency_user FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

CREATE INDEX idx_idempotency_expires ON idempotency_records(expires_at);
```
The UNIQUE constraint already creates the `(idempotency_key, user_id)` lookup index, so there is no second one. `created_at` is the start of the current attempt (it moves forward when a key is reused) and, like `expires_at`, is stored in whole seconds.

### 2. Architecture & Components
- `com.campus.reservation.domain`: `IdempotencyRecord` (entity; state changes only through `markCompleted`, `markFailed`, `restart`) and `IdempotencyStatus` (`IN_PROGRESS`, `COMPLETED`, `FAILED`).
- `com.campus.reservation.repository`: `IdempotencyRecordRepository` with `findByIdempotencyKeyAndUserId(key, userId)` and `deleteExpiredRecords(cutoff)`.
- `com.campus.reservation.service.IdempotencyService`:
  - `computeFingerprint(userId, method, path, payload)`: SHA-256 (hex) of user id, upper-cased method, path and the payload as JSON.
  - `execute(key, userId, method, path, payload, responseType, action)`:
    1. No key (null or blank): runs `action` directly.
    2. Key longer than 128 characters, or not printable ASCII without spaces: `400 INVALID_IDEMPOTENCY_KEY` (a too-long key used to fail the INSERT and look like a 409).
    3. `claimKey`, in its own `REQUIRES_NEW` transaction so a parallel request sees the row at once:
       - no row: insert `IN_PROGRESS` (flushed immediately; a lost race on the unique index becomes `409 CONCURRENT_IDEMPOTENT_REQUEST`);
       - expired row: `restart` it;
       - other fingerprint: `400 IDEMPOTENCY_KEY_PAYLOAD_MISMATCH`;
       - `COMPLETED`: replay (see below). A COMPLETED row is never deleted or restarted, because that would run the booking twice;
       - `IN_PROGRESS` younger than 60 s: `409 CONCURRENT_IDEMPOTENT_REQUEST`; older than 60 s: treated as abandoned and restarted;
       - `FAILED`: `restart` it.
    4. Runs `action`. On success the row becomes `COMPLETED` with the status and JSON body (own `REQUIRES_NEW` transaction). On a `RuntimeException` the row becomes `FAILED` and the exception is rethrown unchanged.
  - Retrying a FAILED key (and taking over an abandoned one) **updates the existing row** back to `IN_PROGRESS` (`IdempotencyRecord.restart`). An earlier version deleted the row and inserted a new one in the same transaction; Hibernate sent the INSERT before the DELETE and hit `uq_idempotency_key_user`, so a retry after FAILED got a 409 for 24 hours.
  - Replay: stored status plus the `Idempotency-Replayed: true` header. If the body cannot be read back (for example the response record changed between deploys) only the status is replayed.
  - **Design choice for a crash between the booking commit and the final save:** the key and the booking are not in one transaction. We chose the simpler option: an `IN_PROGRESS` row older than 60 s (`ABANDONED_AFTER`) counts as abandoned and the key may be used again. Trade-off: if the app died after the booking committed, the retry books again. We accept that instead of locking the student out for 24 h; a booking takes well under a second, so 60 s is far above a real run.
  - **A replay returns the snapshot taken at booking time**, even if the booking was cancelled or transferred since. That is normal for idempotency.

### 3. Autonomous Purge Job (Every 2 Days)
- `IdempotencyService.sweepExpiredRecords()` runs via `@Scheduled(fixedDelayString = "${app.reservation.idempotency-cleanup-ms:172800000}", initialDelayString = "${app.reservation.idempotency-cleanup-initial-delay-ms:600000}")`.
- Fixed delay 172,800,000 ms (2 days). It deletes rows with `expires_at < now` (`idx_idempotency_expires`), in a `@Transactional` method.

### 4. Controller Integration
`ReservationController`:
- `POST /api/v1/reservations` returns `ResponseEntity<ReservationResponse>`.
- `POST /api/v1/reservations/bundle` returns `ResponseEntity<MultiAssetReservationResponse>`.
- Both accept the optional header `@RequestHeader(value = "Idempotency-Key", required = false)`.
- **The frontend does not send `Idempotency-Key` yet**, so the feature is not used by the app today; it works for API clients. Adding the header in `frontend/src/api/reservations.ts` is a follow-up.
