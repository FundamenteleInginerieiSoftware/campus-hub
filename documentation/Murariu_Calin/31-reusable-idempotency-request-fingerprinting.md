## Part 1: In simple terms

In distributed web applications, network glitches, mobile timeouts, and double-clicks regularly cause clients to retry HTTP POST requests. Without idempotency protection:
1. A student clicking "Book" on a spotty Wi-Fi connection might submit two identical requests.
2. If both succeed, the student consumes two active booking quota slots.
3. If one succeeds and the other fails on overlap, the student receives an error screen even though their reservation was successfully registered, causing panic and repeated clicks.

To eliminate this class of issues, we implemented a robust **Idempotency Framework** with **Request Fingerprinting**:
- **Client Header (`Idempotency-Key`)**: The client attaches a unique UUID in the HTTP header `Idempotency-Key` (e.g., generated per UI button click).
- **Request Fingerprinting (SHA-256)**: The server computes a SHA-256 digest of the user ID, HTTP method, target URI, and normalized request body.
- **Cached Replay**: If the same key is submitted again, the server intercepts the call and serves the original HTTP response status code and JSON payload directly from the database, accompanied by the HTTP response header `Idempotency-Replayed: true`.
- **Payload Mismatch Detection**: If a client attempts to reuse an existing idempotency key with different parameters (e.g. attempting to book a different asset or different time slot with an old key), the server rejects it immediately with HTTP 400 (`IDEMPOTENCY_PAYLOAD_MISMATCH`).
- **Concurrent In-Flight Guard**: If two identical requests hit the server concurrently within milliseconds, the first request atomically claims the key in the database with status `IN_PROGRESS`. The second request detects the in-progress state and is immediately rejected with HTTP 409 (`IDEMPOTENCY_CONCURRENT_REQUEST`), preventing race conditions.

## Part 2: Technical details

### 1. Database Schema (`idempotency_records`)
Created in Flyway migration `V2026_11_10_0200__reservation_idempotency.sql`:
```sql
CREATE TABLE idempotency_records (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    idempotency_key VARCHAR(128) NOT NULL,
    user_id BIGINT NOT NULL,
    request_hash VARCHAR(64) NOT NULL,
    status VARCHAR(32) NOT NULL,
    status_code INTEGER,
    response_body TEXT,
    created_at TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    completed_at TIMESTAMP WITHOUT TIME ZONE,
    expires_at TIMESTAMP WITHOUT TIME ZONE NOT NULL,
    CONSTRAINT uq_idempotency_key_user UNIQUE (idempotency_key, user_id)
);

CREATE INDEX idx_idempotency_lookup ON idempotency_records (idempotency_key, user_id);
CREATE INDEX idx_idempotency_expires_at ON idempotency_records (expires_at);
```

### 2. Architecture & Components
Located in package `com.campus.reservation.idempotency`:
- **`IdempotencyRecord`**: JPA Entity modeling state transitions (`IN_PROGRESS`, `COMPLETED`, `FAILED`).
- **`IdempotencyRecordRepository`**: Spring Data JPA repository with `findByKeyAndUserId(key, userId)` and query methods for cleanup.
- **`IdempotencyService`**:
  - `computeRequestHash(userId, method, uri, payload)`: Normalizes payload JSON and computes `SHA-256` in hex representation.
  - `executeIdempotent(key, userId, method, uri, payload, action)`:
    - If `key` is null or blank, executes `action` normally without overhead (passthrough).
    - Checks for existing record.
    - If `COMPLETED`: verifies `requestHash`. If mismatch, throws `ConflictException("IDEMPOTENCY_PAYLOAD_MISMATCH")`. If match, deserializes and returns cached `ResponseEntity<T>` with `Idempotency-Replayed: true`.
    - If `IN_PROGRESS`: throws `ConflictException("IDEMPOTENCY_CONCURRENT_REQUEST")`.
    - If absent: atomically inserts `IdempotencyRecord` (`IN_PROGRESS`) in an isolated `Propagation.REQUIRES_NEW` transaction. Catches `DataIntegrityViolationException` in case of exact database-level race condition.
    - Executes the business logic `action`.
    - On success: saves response status code and JSON serialized body, updates status to `COMPLETED` via `Propagation.REQUIRES_NEW`.
    - On runtime exception: updates status to `FAILED` or deletes record so that future retries are not permanently locked out.

### 3. Controller Integration
Integrated into `ReservationController.java`:
- `POST /api/v1/reservations`: accepts `@RequestHeader(value = "Idempotency-Key", required = false) String idempotencyKey`.
- `POST /api/v1/reservations/bundle`: accepts `@RequestHeader(value = "Idempotency-Key", required = false) String idempotencyKey`.
- Seamlessly returns `ResponseEntity<ReservationResponse>` or `ResponseEntity<List<ReservationResponse>>` with original status `201 CREATED` or replayed `200/201`.
