# 19. Blocarea temporară a unui interval (Reservation Hold) și expirarea automată

**Author:** Calin Murariu ([@Swiorx](https://github.com/Swiorx))  
**Module:** `reservation`  
**Endpoints:** `POST /api/v1/reservations/holds`, `POST /api/v1/reservations/holds/{id}/confirm`, `POST /api/v1/reservations/holds/{id}/release`, `GET /api/v1/reservations/holds/active`  
**Database Table:** `reservation_holds`  

---

## Partea 1: Pe înțelesul tuturor (In simple terms)

### De ce este utilă această funcționalitate?
Când un student vrea să rezerve un echipament de laborator (de exemplu un osciloscop sau un generator de semnal), acesta trece prin câțiva pași:
1. Găsește intervalul orar liber (de exemplu miercuri 14:00 – 16:00).
2. Deschide fereastra de confirmare, își verifică orarul și pregătește rezervarea.

Într-un sistem obișnuit fără mecanism de reținere (hold), un alt coleg poate rezerva exact același echipament în acele câteva secunde în care primul student se uită la detalii, generând o eroare neplăcută de conflict la apăsarea butonului final („Confirmă”).

### Cum funcționează „Reservation Hold”?
Sistemul introduce un mecanism de **rezervare temporară (Hold)** pe o durată de **1 minut (60 de secunde)**:
- În momentul în care studentul selectează intervalul, sistemul „blochează” temporar slotul pentru el.
- Pe durata acelui minut, niciun alt student nu poate rezerva sau bloca același interval.
- **Dacă studentul finalizează rezervarea:** Intervalul temporar se transformă instantaneu într-o rezervare confirmată oficială.
- **Dacă studentul renunță sau închide fereastra:** Poate elibera blocarea manual (butonul „Anulează”), iar slotul devine imediat disponibil colegilor.
- **Dacă studentul abandonează procesul:** După scurgerea minutului, blocarea expiră automat (`EXPIRED`), iar un proces de fundal (job automat) eliberează resursa.

Pentru a preveni abuzurile (de exemplu un student care ar bloca toate cele 10 osciloscoape din laborator), fiecare student are voie la **maximum 1 hold activ**.

## Partea 2: Detalii tehnice (Technical details)

### 1. Arhitectură și Model de Date

Tabela PostgreSQL `reservation_holds` este gestionată prin migrarea Flyway `V2026_11_08_1630__reservation_create_holds.sql`:

```sql
CREATE TABLE reservation_holds (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    asset_id BIGINT NOT NULL REFERENCES assets(id),
    user_id BIGINT NOT NULL REFERENCES users(id),
    start_time TIMESTAMP NOT NULL,
    end_time TIMESTAMP NOT NULL,
    expires_at TIMESTAMP NOT NULL,
    status VARCHAR(32) NOT NULL,
    created_at TIMESTAMP NOT NULL,
    version BIGINT NOT NULL DEFAULT 0
);
```

#### Indexare pentru performanță și concurență
- `idx_reservation_holds_asset_slot (asset_id, status, expires_at, start_time, end_time)`: interogare ultra-rapidă pentru verificarea suprapunerilor active în timpul creării de hold-uri sau rezervări.
- `idx_reservation_holds_user_active (user_id, status, expires_at)`: verificarea limitei de 1 hold activ per student.
- `idx_reservation_holds_expiry_sweep (status, expires_at)`: interogare eficientă pentru job-ul periodic de curățare a hold-urilor expirate.

### 2. Mașina de Stări a Hold-ului (`HoldStatus`)

```
                  ┌──────────────┐
                  │    ACTIVE    │
                  └──────┬───────┘
                         │
        ┌────────────────┼────────────────┐
        │ confirm()      │ release()      │ expire() (după 1 min)
        ▼                ▼                ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│  CONFIRMED   │ │   RELEASED   │ │   EXPIRED    │
└──────────────┘ └──────────────┘ └──────────────┘
```

1. **`ACTIVE`:** Creat la `POST /api/v1/reservations/holds`. `expiresAt = now + 1 minut`.
2. **`CONFIRMED`:** Tranzacționat atomic prin `POST /api/v1/reservations/holds/{id}/confirm`. Creează înregistrarea în `reservations`, auditează și trimite notificare prin `NotificationService`.
3. **`RELEASED`:** Anulat anticipat prin `POST /api/v1/reservations/holds/{id}/release`.
4. **`EXPIRED`:** Marcat automat dacă `now >= expiresAt`.

### 3. Gestionarea Concurenței și Prevenirea Race Conditions

Pentru a garanta că două cereri concurente nu pot rezerva sau bloca același interval la aceeași milisecundă:
1. **Blocare pesimistă de rând (`CatalogApi.lockForBooking`):** Prima atingere a bazei de date blochează rândul din tabela `assets` (`SELECT ... FOR UPDATE`), serializând cererile concurente pe același echipament.
2. **Advisory Lock pe cota utilizatorului (`lockUserQuota`):** Previne depășirea concurentă a cotei de 2 rezervări active sau a limitei de 1 hold activ.
3. **Pessimistic Lock la Confirmare (`findByIdForUpdate`):** La confirmare, rândul din `reservation_holds` este blocat pesimist pentru a preveni apeluri duble paralele (`confirmHold`).

### 4. Job de Fundal Automatizat (`ReservationLifecycleService`)

Hold-urile expirate sunt curățate automat în două moduri:
- **Activ în interogări:** Toate verificările de disponibilitate și suprapunere filtrează `status = 'ACTIVE' AND expires_at > :now`. Un hold al cărui TTL a expirat nu mai blochează slotul chiar înainte de rularea job-ului de sweep.
- **Job autonom `@Scheduled`:**
  ```java
  @Scheduled(
      fixedDelayString = "${app.reservation.hold-sweep-ms:60000}",
      initialDelayString = "${app.reservation.hold-initial-delay-ms:30000}")
  public int sweepExpiredHolds() {
      LocalDateTime now = now();
      return reservationService.sweepExpiredHolds(now);
  }
  ```
  Job-ul execută un query de tip `UPDATE reservation_holds SET status = 'EXPIRED' WHERE status = 'ACTIVE' AND expires_at <= :now`.

### 5. API Endpoints & Coduri de Eroare

| Metodă | Endpoint | Descriere | Răspuns |
|---|---|---|---|
| `POST` | `/api/v1/reservations/holds` | Creează un hold de 1 minut pe interval | 201 Created (`ReservationHoldResponse`) |
| `POST` | `/api/v1/reservations/holds/{id}/confirm` | Confirmă hold-ul și creează rezervarea | 200 OK (`ReservationResponse`) |
| `POST` | `/api/v1/reservations/holds/{id}/release` | Eliberează hold-ul anticipat | 200 OK (`ReservationHoldResponse`) |
| `GET` | `/api/v1/reservations/holds/active` | Returnează hold-urile active ale studentului | 200 OK (`List<ReservationHoldResponse>`) |

#### Coduri de eroare specifice:
- `404 HOLD_NOT_FOUND`: Hold-ul nu există sau aparține altui utilizator (protecție IDOR).
- `409 HOLD_EXPIRED`: Minutul a expirat; hold-ul nu mai poate fi confirmat.
- `409 SLOT_HELD`: Intervalul selectat este blocat temporar de un alt student.
- `409 ACTIVE_HOLD_LIMIT_REACHED`: Studentul are deja un hold activ (maximum 1 permis).
- `409 RESERVATION_LIMIT_REACHED`: Cota maximă de 2 rezervări active ar fi depășită.
- `409 INVALID_HOLD_STATUS_TRANSITION`: Încercare de a confirma/elibera un hold care nu este în starea `ACTIVE`.
