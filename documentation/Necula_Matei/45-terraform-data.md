## Part 1: In simple terms

1. **The database (PostgreSQL 18 on RDS) is written down, but switched off.** It is the only piece here that costs money every hour it exists (about $0.50 a day), and it is useless until the app server exists (W7). One switch (`db_enabled`) turns it on for the first deploy.
2. **A private bucket for incident photos.** The app saves photos there on AWS. Nobody can open it from the internet: photos are only shown through the app, which checks who may see them.
3. **A registry for the app's Docker image (ECR).** Every image gets the name of its commit, and a name can't be reused, so "go back to version x" always gets exactly what was tested. Only the last 10 images are kept, to keep storage cheap.
4. **A place for the app's logs**, kept 7 days.
5. **The server's own permissions (a role).** The app on the server can save and read photos in our bucket, send e-mails, read its own settings, pull its image and write logs. Nothing else, and only on our own resources. No AWS keys are stored anywhere: the server borrows these permissions from AWS.
6. **The secrets are made by Terraform.** The database password and the login-token secret are random, generated by Terraform, and stored encrypted in AWS (SSM Parameter Store). No person ever types or sees them.

**Result:** everything the app needs on AWS, apart from the server and CloudFront (W7), exists as code and passes `terraform validate`. With the database off, all of it costs well under $1 a month.

## Part 2: Technical details

| File | What it holds |

| `infra/storage.tf` | Photo bucket (private, AES256, `force_destroy`), ECR repository `campus-hub` + lifecycle policy, log group `/campus-hub/app` |
| `infra/iam.tf` | Role + instance profile `campus-hub-app`, 2 AWS-managed policies, 1 inline policy (5 statements) |

| `infra/variables.tf` | New `db_enabled` (bool, default `false`) |
| `infra/outputs.tf` | New `photo_bucket`, `ecr_repository_url`, `app_instance_profile`, `db_endpoint` (null while the DB is off) |

### `db_enabled`: why RDS stays off

| Setting | Value | Why |
|---|---|---|
| `db_enabled` | `false` by default | ~$0.50/day (~$15/month) for nothing until W7. Turn on with `terraform apply -var db_enabled=true` |
| Engine | `postgres` `"18"`, `db.t4g.micro`, 20 GB `gp3`, encrypted | Same major version as laptops and CI. `"18"` = newest 18.x; AWS applies minor updates in the maintenance window |
| `db_name` / `username` | `campus` / `campus` | Same as every laptop (AGENTS.md §5), so `DB_URL` is the only difference |
| `publicly_accessible` | `false` | Private subnets + security group: only the app server reaches it (part 1) |
| `multi_az` | `false` | Budget. "Multi-AZ in production" goes in the report |
| `backup_retention_period` | `1` | One daily snapshot, enough to practise a restore in W10 |
| `deletion_protection` / `skip_final_snapshot` | `false` / `true` | `terraform destroy` works without manual steps and leaves no paid snapshot. In production both would be the other way round |
| `apply_immediately` | `true` | A change (e.g. a new password) applies now, not in the weekly maintenance window |

**Careful:** setting `db_enabled` back to `false`, or running a later `terraform apply` **without** `-var db_enabled=true`, deletes the database and its data, with no final snapshot. Once the DB is on, pass the flag every time; the W7 deploy PR flips the default in `variables.tf` to `true` so nobody can forget it.

### IAM: what the server may do

The role can only be worn by EC2 (`sts:AssumeRole` for `ec2.amazonaws.com`); EC2 gets it through the instance profile. The AWS SDK in the container finds the credentials through the instance metadata on its own (`AwsConfig`, doc 23).

| Permission | On | Needed by |
|---|---|---|
| `s3:PutObject`, `s3:GetObject`, `s3:DeleteObject` | `<photo-bucket-arn>/*` | `S3StorageService` (#129): store, load, delete photos |
| `s3:ListBucket` | `<photo-bucket-arn>` | `S3StorageService`: without it S3 answers 403 instead of 404 for a missing photo, so the code can't tell "not found" from "not allowed" (#177, doc 29) |
| `ses:SendEmail` | `*` | `SesNotificationService` (#129). SES itself limits it: only verified sender identities (W9), and only verified recipients while in the SES sandbox |
| `ssm:GetParameter`, `GetParameters`, `GetParametersByPath` | `parameter/campus` + `parameter/campus/*` | Deploy script (W8): reads `/campus/*` into the container's env file (ADR-003). Two ARNs because `GetParametersByPath` is checked against the folder itself, which `/*` alone doesn't match. No `kms:Decrypt`: the AWS-managed `aws/ssm` key already allows decryption through SSM |
| `logs:CreateLogStream`, `logs:PutLogEvents` | `<log-group-arn>:*` | Docker `awslogs` driver (W7): container output into `/campus-hub/app` |
| `AmazonSSMManagedInstanceCore` (AWS-managed) | | Session Manager (our shell, no SSH) and Run Command (the W8 deploy) |
| `AmazonEC2ContainerRegistryReadOnly` (AWS-managed) | | `docker pull` of our image from ECR |

### SSM parameters → environment variables

Each parameter name is exactly the variable `application-prod.yml` reads, so the deploy script can turn `/campus/*` into an env file without a mapping table (env table in doc 23).

| Parameter | Type | Value from | Env var | Status |
|---|---|---|---|---|
| `/campus/DB_URL` | String | `jdbc:postgresql://<rds-endpoint>/campus?sslmode=require` | `DB_URL` | Only while `db_enabled = true` (needs the RDS host name). `sslmode=require`: the driver refuses an unencrypted connection instead of quietly falling back |
| `/campus/DB_USERNAME` | String | `campus` | `DB_USERNAME` | Done |
| `/campus/DB_PASSWORD` | SecureString | `random_password.db` (32, letters + digits) | `DB_PASSWORD` | Done |
| `/campus/JWT_SECRET` | SecureString | `random_password.jwt` (64 characters = 64 bytes) | `JWT_SECRET` | Done. HS256 needs ≥ 32 bytes, a shorter one fails at startup (doc 23) |
| `/campus/AWS_REGION` | String | `var.aws_region` | `AWS_REGION` | Done |
| `/campus/PHOTO_BUCKET` | String | the photo bucket name | `PHOTO_BUCKET` | Done |
| `/campus/MAIL_FROM` | | a verified SES sender | `MAIL_FROM` | **Missing.** Required: the app won't start without it, so it must exist **before the first deploy** (needs the SES identity, W9 in the plan → move it earlier) |
| `/campus/ADMIN_EMAIL`, `/campus/ADMIN_PASSWORD` | | | `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Missing, optional: first admin on AWS (doc 18). Without them nobody can log in as admin on a fresh RDS |
| | | | `SPRING_PROFILES_ACTIVE` | Not a parameter: the Dockerfile sets `prod` (doc 19) |
| | | | `SQS_QUEUE_URL` | Optional, SQS stretch goal only |

`special = false` on both passwords: RDS rejects `/`, `@`, `"` and spaces in the master password, and letters + digits are plenty at that length. Both values end up in the Terraform state, which is why the state lives only in the encrypted S3 bucket (part 1).

### ECR, photos and logs

| Resource | Setting | Why |
|---|---|---|
| ECR `campus-hub` | `image_tag_mutability = "IMMUTABLE"` | Each image is tagged with its commit SHA (ADR-002 deploy). A tag can't be pushed twice, so a rollback to SHA x gets exactly the tested image |
| | `scan_on_push = true` | Free basic scan for known vulnerabilities |
| | lifecycle: `imageCountMoreThan 10` → expire, `tagStatus = "any"` | Storage is billed per GB (~300 MB per image); old images are only for rollback |
| | `force_delete = true` | `terraform destroy` works with images inside |
| Photo bucket `campus-hub-photos-<suffix>` | public access blocked, AES256 | Photos are served only through Stefania's `GET /incidents/{id}/photo`, which checks who may see them |
| | `force_destroy = true` | Test photos go away with `terraform destroy` |
| Log group `/campus-hub/app` | `retention_in_days = 7` | Without a retention CloudWatch keeps (and bills) logs forever |

### `terraform destroy`

ADR-001: we delete everything between work phases and recreate it in minutes.

| What | On `terraform destroy` in `infra/` |
|---|---|
| RDS | Deleted, no final snapshot (`skip_final_snapshot`), automated backups gone. All data lost |
| Photo bucket, ECR | Deleted with their content (`force_destroy`, `force_delete`) |
| SSM parameters, role, log group, network | Deleted |
| `random_password`, `random_id` | Deleted. The next `apply` makes **new** values: new DB password, new JWT secret (everyone logs in again), new photo bucket name. The SSM parameters follow on their own |
| State bucket | **Kept**: it belongs to `bootstrap/`, a separate config with `prevent_destroy` |

Same as part 1 (`44-terraform-network.md`), from `infra/`:

### Problems and open points

| Point | Notes |
|---|---|
| `MAIL_FROM` before the first deploy | The app refuses to start without it. Needs a verified SES identity, which the plan put in W9 |
| `db_enabled` must be passed on every apply once on | Otherwise Terraform plans to delete the database (see the warning above) |
| No admin on a fresh RDS | Until `ADMIN_EMAIL` / `ADMIN_PASSWORD` exist in SSM, `AdminBootstrap` does nothing (doc 18) |
| Two `random_id "suffix"` | One in `bootstrap/` (state bucket), one in `storage.tf` (photo bucket). Separate configs, so two different suffixes; that's fine |
